## 0. このSummit全体の空気

**エージェント一色。** 150件中78件が生成AI/エージェント、AgentCore言及47件、MCP 62件、Kiro 37件。
しかも論調は「試してみよう」ではなく **「PoCから本番へ、どう運用するか」** に移っている。
セッションタイトルに「本番運用を見据えた」「PoCを乗り越える」「production-minded」が並ぶ。

**ただし成果は出ていない。** PwC調査（PRT237）が身も蓋もない数字を出している:

| | 2024 | 2025 |
|---|---|---|
| 生成AIを「活用中」 | 43% | **56%**（+13pt） |
| DX成果が「期待通り以上」 | 41% | **38%**（−3pt） |

**使う企業は増えたのに、成果実感はむしろ下がった。** PRT237の診断は
「技術面ではなく組織に仕組みがないことが問題。個別に乗り越えようとすれば属人化と車輪の再発明が加速」。

→ **判断材料としての含意**: ツール導入の是非より「仕組み化されているか」を先に問うべき、というのが
今年の資料群の一致した見立て。これは仕組み化で勝負する自分の方針と整合する。

## 1. AIエージェントを作る/運用するときの判断

### 1-1. 精度が出ないときにどこを触るか（AIM314）

AWSは改善軸を **Architecture / Context / Tools** の3つに整理している。

**Architecture**
- ユースケースを整理してからアーキテクチャを選ぶ
- 自律性の高さと制御の難しさは**トレードオフ**
- 要件を満たす**一番シンプルな**構成を採る

**Context — 「多いほど良い」は誤り**
- Context Rot / Lost in the Middle で**性能が落ちる**。必要最小限に抑える
- セッション内は Sliding Window / Summarization で圧縮
- セッション横断は長期メモリ側に逃がす

**Tools**
- ツール定義は簡潔に（エージェントが使いやすい形）→ 利用エラーが減る
- ツールが多いなら動的に必要な分だけ取得（Semantic Tool Search）→ 選択エラーが減る
- **リトライしやすいエラー設計** + セッションあたりのツール実行回数に上限 → 無駄なリトライが減る

> これは自分のCLAUDE.mdの「コンテキストウィンドウ管理が最重要」と同じ結論に
> AWS側も到達している。裏が取れたと考えてよい。

### 1-2. 本番に出すときの9ルール（AIM342）

1. 課題から逆算して小さく始める
2. ツールとAPI連携を計画する
3. **オブザーバビリティを初日から**設定する
4. エージェントの評価を自動化する
5. マルチエージェントを検討する
6. パーソナルエージェントをセキュアに構築する
7. **できるだけコードを使う**（GUI/ノーコードに寄せすぎない）
8. 何度も繰り返しテストする
9. 組織体制を整えて規模を拡大する

PoC→本番で詰まる論点は「ビジネス価値・パフォーマンス・スケーラビリティ・ガバナンス・セキュリティ」。

### 1-3. 何を計測するか

- **OpenTelemetry で計装 → CloudWatch 生成AIオブザーバビリティで可視化 → AgentCore Evaluations で継続評価**（CNS317）
- トレース構造は セッション > トレース > スパン > サブスパン
- 実務事例では **Langfuse** が複数社で採用されている（ARC317, AIM322, AIM312）
- ARC317（B2B SaaS）の工夫が秀逸: **OTel Collector層で入力をマスクし、オンラインLLM-as-a-judgeでスコアだけ保存**。
  顧客データを見ずに品質をモニタリングできる。データポリシーと改善サイクルの両立策として使える

### 1-4. セキュリティの型

- **OWASP Top 10 for Agentic Applications**（ASI01-06）が共通言語になりつつある
  （Goal Hijack / Tool Misuse / Identity & Privilege Abuse / Unexpected Code Execution / Memory & Context Poisoning）
- **3つの境界**で考える: ユーザー境界 / ネットワーク境界 / アカウント境界（BIZ204 デジタル庁）
- 「全アクションを**実行前に**ポリシーで検査」「セッションを分離」（AIM201）
- **最終的な制御は決定的な仕組みに委ねる。LLMは対話と推論だけ**（AIM344）— これが一番効く原則
- 電通（MAM241）は140社に対し「認証・制御ポイント・観測」を一元化する構想。
  エージェントの個別ID乱立を抑える発想は、ルーティンが増えたときに効いてくる

### 2-1. 効果として報告されている数字

| 出典 | 内容 | 効果 |
|---|---|---|
| AIM221 | AI-DLC実証（120SP規模） | 12週 → **6週**、品質+30% |
| AIM310 | Todoアプリ（VibeCoding） | 15.5人日 → **2.0人日（−87%）** |
| AIM213 東京海上 | AI駆動開発 試行 | スピード**10倍**、生産性**3倍** |
| PRT141 JAL | Platform Engineering | 開発リードタイム165日 → **30分** |
| AIM234 オムロン | 知財AIエージェント | 特許調査工数**50%減** |
| AIM226 Umios | 需要予測 | 作業**4,200時間**削減 |
| MAM303 | メインフレームReimagine | 年単位 → **月単位** |

> 注意: いずれも**発表者による自己申告**で、条件も規模もバラバラ。
> 特にAIM310の−87%は小さなTodoアプリ1本の話なので、そのまま一般化はできない。

### 2-2. 資料が正直に認めている弱点

- **「Vibesのノリのままだと大規模開発に使えない」**（AIM310）。組織的に使うにはスキームの定義が要る
- **「AIでコードは書けても、レビューできる人がいなくなる」**（AIM223）。
  自動化のパラドックスを正面から扱ったセッション。AI-DLCを「鏡」として弱点を可視化し、
  **意図的な非効率で育成を埋める**という主張
- **AIの実力の見積もり方**（PRT340 TIS）: 「能力はジュニアレベルだが、超高速に休みなく働いてくれる社員」
- **正確性が要るタスクにAIを置いても効果は薄い**（PRT340）。
  Human-in-the-Loopが前提になるので最終判断の人的コストが残る。
  → **打ち手は「業務プロセスの再設計」**。レビュー工程にAIを入れるのではなく、
  **一次作成の品質を上げて**レビュー負荷を下げる。精度80%でも即日フィードバックなら勝てる

### 2-3. コードをAIに優しくする（CNS449）

- Monorepoは肥大するとエージェントが大量ファイルを読んで**コンテキストを圧迫する**
- 対策は「パッケージの依存関係を最小限にし、**細部を見なくても理解できる構造**を作る」

## 3. 運用・SRE（自分の本業に直結）

### 3-1. AWS DevOps Agent の設計原則（CNS319）

- **Agent Space は調査スコープに合わせる**
- 依存先まで含めて1つのAgent Spaceにまとめる（アカウントをまたいでも同一システムなら1つ）
- 環境やチーム単位では分ける

### 3-2. 「なぜ運用はAIで楽にならないのか」（PRT211 PagerDuty）

タイトルが問いそのもの。前提として「2025年=AIエージェント元年、開発は激変した」が、
**運用側は同じようには楽になっていない**という問題提起。

### 3-3. 運用にAIを入れる順番（PRT215 NEC）

1. **定型業務**の手間を減らし、非定型に集中する（情報収集・アラート対応・改善活動の3領域）
2. ガバメントクラウドでも生成AIは使える（3条件を満たすサービス選定が出発点）
3. **受け身から、問いかける運用へ**

### 3-4. レジリエンス / ランサム対策（STG205, PRT210, ARC339）

- **「侵入を完全に防ぐことはできない」を前提に**、被害抑制と確実な復旧を設計する（PRT210 パルグループ実例）
- バックアップの**イミュータブル化が最優先**: AWS Backup Vault Lock（WORM）、S3 Object Lock
- Vault Lockは既存Vaultで有効化すると取得済みバックアップが**手動削除不可**になる点に注意
- インシデント対策は「準備したら完了」ではなく**継続運用**が最重要
- ARC339はSTSグローバルエンドポイントの10年がかりのリージョン分離史を扱っている。
  **AWS側の改善を待つのではなく、利用者側で先に手を打つ**教訓として読める

## 4. コスト / FinOps

### 4-1. 三井住友信託の「実現できるコスト最適化」（PRT202）

現場で回すための5原則。抽象論がなく実用的:

1. **完璧主義を排除**し、まずできる事からやる。ベストプラクティスの実践からスタート
2. コスト情報は**可視化**し、利用者がいつでも見られる状態に
3. **経営層にコミット**させ、推進の後ろ盾になってもらう
4. 自社のAWS運用を把握しているチーム/メンバーを**主体**にする
5. 継続する**体制**を作り、定期的に評価・見直し

具体施策例: 30日以上未使用のWorkSpacesをEventBridge+Lambdaで日次検知・自動削除

### 4-2. 前提となる数字

- クラウド支出の管理を課題とする企業が**85%**、自己申告の無駄は**29%**（PRT221 / Flexera）
- 技術的負債はIT予算の**20%**、開発者時間の**23%**を食う（MAM204 / Forrester他）

### 4-3. LLMのコスト構造（AIM312 freee — 月100万件AI-OCR）

自前SLMに切り替えるかの判断基準が明快。**汎用LLMを使い続けるか自前かの意思決定フレームとして使える**:

- **LLMはtoken課金、SLMは時間課金**。この違いを理解して見積もる
- イニシャル（学習・評価）とランニング（推論・運用）を**分けて**見積もる
- 運用コストは **output token/sec** を測れば自ずと決まる
- SLM化すべきタスクの条件: ①入出力スキーマが安定 ②汎用LLM（Claude Haiku等）で既に安定して解けている
  ③件数が多くコスト/速度がビジネスに効く ④評価データを継続的に作れる体制がある
- **「SLMはモデル開発ではなく本番システム開発」** — 評価・監視・改善込みで見ろ

### 4-4. モデルは大きければいいわけではない（AIM118 コーエーテクモ）

ゲーム内チャット翻訳の事例。**「翻訳に特化するなら軽量で安価なモデルで十分、速度も問題にならない」**。
ユーザーの自由入力は一文が短く、軽量モデルと相性が良い。
プロンプトキャッシュ活用でコストを下げる（PRT231）も併記されている。

## 5. 組織・進め方（成果が出ない企業との差）

### 5-1. 成果を出した組織の共通項

- **三菱電機 AICoE**（AIM228）: トップエンジニア編成 / 組織トップと方針合意（予算と体制を早期確保） /
  寄り添う勉強会（**置いてきぼりを作らない**） / 人材ローテーション（各組織にAIネイティブを配置） /
  外部コミュニティとの対話。**技術起点 × トップダウン × 現場密着を同時に成立**させる
- **サイバーエージェント**（AIM229）: 部署ごとのAI活用状況を**相撲の番付表**に見立てて可視化し底上げ
- **Umios**（AIM226）の3つの学び: ①効果は**データ品質**が左右 ②**技術選定より運用設計**に時間を
  ③現場が回る運用を事業部と作る
- **東京電力**（AIM240）: できる限り**標準機能**を使いスクラッチを最小化 → 10か月でリリース、3か月で18拠点展開。
  「試しながら精度向上」を並行実施

### 5-2. 成果が出ない構造（PRT237 PwC）

壁を個人の努力で越えるのではなく、**組織の力で壁そのものをなくす**:
- 業務部門とIT部門一体でのアジャイルな組織運営
- Platform Engineeringによる**再発明の防止**
- 自走化を支える組織設計と役割別育成
