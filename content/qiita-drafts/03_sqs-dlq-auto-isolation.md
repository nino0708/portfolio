# SQS デッドレターキュー（DLQ）で失敗した処理を自動隔離する

<!-- tags: AWS, SQS, Lambda, サーバーレス -->
<!-- status: 下書き -->

## DLQとは

処理に失敗したメッセージを自動的に別のキューに移動させる仕組み。

通常キューで規定回数（最大受信数）を超えて処理に失敗したメッセージは、自動的にデッドレターキューへ転送される。

---

## 通常キューとDLQの関係

```
SQS キュー（メイン）
    ↓ 処理失敗 × 最大受信数
SQS DLQ（デッドレターキュー）
    ↓
後で確認・再処理・原因調査
```

---

## 設定のポイント

### 最大受信数（maxReceiveCount）
メインキューで何回失敗したらDLQに移すかを設定する。推奨は3〜5回。

### メッセージ保持期間
DLQ のメッセージ保持期間はメインキューより長く設定しておく（デフォルト4日、最大14日）。原因調査の時間を確保するため。

---

## Lambda + SQS + DLQ の構成

```
API / AppSync
    ↓
SQS（注文キュー）
    ↓
Lambda（注文処理）
    ↓ 失敗 × n回
SQS DLQ（失敗注文の隔離）
    ↓
CloudWatch アラーム（DLQにメッセージが入ったら通知）
```

---

## DLQ vs Kinesis の違い（よく混同するポイント）

| | SQS + DLQ | Kinesis |
|---|---|---|
| 用途 | タスクキュー（1件ずつ処理） | ストリーム処理（時系列データ） |
| 失敗の自動隔離 | **DLQで自動転送** | なし（リトライ設定のみ） |
| 順序保証 | 基本的になし（FIFOキューで可） | シャード内で保証 |

「失敗した処理を自動隔離して後で再処理したい」→ SQS + DLQ が答え。

---

## AppSync が選ばれる理由（SAPでよく出る構成）

DLQと組み合わせる際、データアクセス層として AppSync が登場することがある。

| サービス | 役割 | サーバーレス |
|---|---|---|
| **AppSync** | GraphQL API + DynamoDBへ直接接続 | ✅ |
| API Gateway | REST API | ✅（Lambdaと組み合わせが必要） |
| EC2 | サーバー | ❌ |

AppSync は DynamoDB へ Lambda を介さず直接接続できる + リアルタイム通信（GraphQL サブスクリプション）が標準機能。ただし**この構成の本質は DLQ による自動隔離の部分**であり、AppSync vs API Gateway の優劣は副次的な話。

---

## まとめ

- SQS DLQ = 失敗メッセージを「自動隔離」して後から再処理できる仕組み
- 最大受信数を超えたメッセージが自動転送される
- DLQ にアラームを設定しておくと障害検知に使える
