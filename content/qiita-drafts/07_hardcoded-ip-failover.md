# ハードコードされたIPアドレスをフェイルオーバー対応にする方法

<!-- tags: AWS, Route53, EC2, 可用性, ネットワーク -->
<!-- status: 下書き -->

## 問題

既存システムでアプリが接続先のIPアドレスをコードや設定ファイルにハードコードしている。
この状態だと、接続先の EC2 や NLB が入れ替わったときにアプリ側の修正が必要になる。

---

## 解決策：Route 53 で DNS 名に切り替える

IPアドレスを直接指定する代わりに、Route 53 の DNS レコードを経由させる。

```
変更前：アプリ → 192.0.2.10（ハードコード）

変更後：アプリ → db.example.internal（DNS名）
                       ↓
               Route 53 プライベートホストゾーン
                       ↓
               192.0.2.10（現在のIP）
```

フェイルオーバー時は Route 53 の A レコードを書き換えるだけでアプリ側の変更が不要になる。

---

## Route 53 フェイルオーバールーティングの設定

### ヘルスチェックと組み合わせる

```
Route 53
├── プライマリレコード（192.0.2.10）
│   └── ヘルスチェック: EC2-A が正常か確認
└── セカンダリレコード（192.0.2.20）
    └── プライマリが異常になったとき自動で切り替わる
```

### 設定手順

1. Route 53 でプライベートホストゾーンを作成（内部向けなら `.internal` ドメイン推奨）
2. プライマリ・セカンダリそれぞれの A レコードを作成
3. ヘルスチェックを作成してプライマリレコードに紐付け
4. アプリの接続先を DNS 名に変更

---

## VPC 内での DNS 解決を有効にする

プライベートホストゾーンを使う場合、VPC の設定が必要。

```
VPC → 設定
├── DNS ホスト名: 有効
└── DNS 解決: 有効
```

---

## NLB（Network Load Balancer）との組み合わせ

複数の EC2 をフェイルオーバー対象にするなら NLB を挟むのが定番。

```
アプリ → Route 53（DNS名）→ NLB → EC2-A
                                 ↘ EC2-B（バックアップ）
```

NLB には固定 IP または EIP を割り当てられるため、NLB 自体の IP を Route 53 に登録しておけば、バックエンドの EC2 が入れ替わっても Route 53 の設定変更は不要。

---

## TTL の設定

フェイルオーバーを素早く行いたい場合、TTL を短くしておく。

| TTL | キャッシュ時間 |
|---|---|
| 300秒（デフォルト） | 5分間古いIPが使われる可能性あり |
| 60秒 | 障害検知から切り替えまでを短縮できる |
| 1秒 | 最速だがDNSクエリ数が増えてコストが上がる |

本番環境では 60〜300 秒が一般的。

---

## まとめ

- ハードコードIPの問題はRoute 53 の DNS 名に置き換えることで解消できる
- フェイルオーバールーティング + ヘルスチェックで自動切り替えが可能
- TTL を短く設定しておくと切り替え時間を短縮できる
